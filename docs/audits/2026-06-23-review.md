## Executive Summary

BurnWatch is an AI token usage tracking system with a well-thought-out architecture: a Bun CLI agent collects ccusage/codeburn data from developer machines, a Fastify 5 API persists it to Neon PostgreSQL, and a Next.js 15 dashboard renders it. The shared package with Zod validation is a strong foundation.

However, the codebase has **critical security issues** (unauthenticated admin endpoints, hardcoded JWT secrets on disk, missing auth on all dashboard API routes, refresh token signed with same secret as access token), **several bugs that will crash at runtime** (missing `return` after Fastify `reply.send()`, `pendingDevices` import not used but referenced tables exist), and **architectural gaps** that would cause data integrity problems at scale (no transaction boundaries, fire-and-forget snapshot rebuilds, unbounded JSONL file reads).

**Risk Score: 7/10** -- Significant issues that will cause production problems. The security posture is not production-ready.

## P0 -- Critical (Must fix before any deployment)

### P0-1: Admin endpoints have ZERO authentication

**File:** `apps/api/src/routes/auth/device.ts` lines 98-141
**Severity:** Critical | **Exploitability:** Trivial

Both `POST /v1/auth/admin/bootstrap` and `POST /v1/auth/admin/users` have no authentication whatsoever. Anyone can:
1. Create new organizations
2. Create admin users in any org
3. Create unlimited users and then register devices to exfiltrate all org data

```typescript
// Line 98 -- no auth middleware, no rate limit
fastify.post('/admin/bootstrap', async (request, reply) => {
  const body = BootstrapSchema.parse(request.body)
  // ... creates org + admin user with no auth check
})
```

**Fix:** Add authentication + role check. At minimum, bootstrap should only work when zero orgs exist (first-run guard), and `/admin/users` must require admin JWT:

```typescript
fastify.post('/admin/bootstrap', async (request, reply) => {
  const existingOrgs = await fastify.db.select({ id: organizations.id }).from(organizations).limit(1)
  if (existingOrgs.length > 0) {
    return reply.status(403).send({ error: 'Bootstrap already completed' })
  }
  // ... proceed
})

fastify.post('/admin/users', {
  preHandler: requireDashboardAuth(fastify),
}, async (request, reply) => {
  if (request.user.role !== 'admin') { ... }
})
```

> **STATUS 2026-11-05: RESOLVED.** Both guards are in the live source.
> `apps/api/src/routes/auth/device.ts:171-178` selects from `organizations` and
> returns 403 `Bootstrap already completed` when a row exists, which is the
> first-run guard proposed here. `/admin/users` at `:204-215` has a `preHandler`
> that calls `accessJwtVerify` and returns 403 unless `payload.role === 'admin'`,
> with 401 on a failed verify. A second check at `:223` rejects creating a user
> in another org. Both routes also carry rate limits (see P3-6).

### P0-2: ALL dashboard API routes have no authentication

**File:** `apps/api/src/routes/dashboard/overview.ts`, `leaderboard.ts`, `trends.ts`, `activity.ts`, `projects.ts`
**Severity:** Critical | **Exploitability:** Trivial

None of the five dashboard endpoints use any authentication. Anyone who knows an `orgId` (which is a UUID, but still guessable via the bootstrap endpoint) can read:
- All org members' names and emails (`/leaderboard` exposes PII)
- Complete spending data
- Project paths (internal infrastructure exposure)
- Activity breakdowns

The `requireDashboardAuth` function exists in `src/plugins/jwt.ts` but is never used anywhere.

**Fix:** Apply auth to the dashboard route group:

```typescript
// apps/api/src/routes/dashboard/index.ts
export async function dashboardRoutes(fastify: FastifyInstance) {
  fastify.addHook('preHandler', requireDashboardAuth(fastify))
  // ... register sub-routes
}
```

And add org-scoping: verify `request.user.orgId === request.query.orgId`.

> **STATUS 2026-11-05: RESOLVED.** `apps/api/src/routes/dashboard/index.ts:11`
> is `fastify.addHook('preHandler', requireDashboardAuth(fastify))`, applied to
> the group before the five sub-routes register. `requireDashboardAuth` is no
> longer dead code. Org-scoping went further than the fix suggested: rather than
> comparing the JWT org against a query param, `orgId` was removed from the query
> contract entirely and every route reads `request.user.orgId`. See P1-2.

### P0-3: Missing `return` after `reply.send()` in auth middleware

**File:** `apps/api/src/plugins/jwt.ts` lines 28-37
**Severity:** Critical | **Exploitability:** N/A (runtime crash)

In `requireDashboardAuth`, when the role check fails, `reply.send()` is called but execution continues. Fastify will attempt to send the response from the route handler too, causing a "Reply was already sent" error.

```typescript
// Line 30-32 -- BUG: no return after reply.send()
if (payload.role !== 'user') {
  reply.status(403).send({ error: 'Dashboard access requires user role' })
  // Execution continues to the route handler!
}
```

The same pattern exists in `requireAuth` (line 22) but is less critical since it's in a catch block.

**Fix:** Add `return` after every `reply.send()`:

```typescript
if (payload.role !== 'user') {
  return reply.status(403).send({ error: 'Dashboard access requires user role' })
}
```

> **STATUS 2026-11-05: RESOLVED.** `apps/api/src/plugins/jwt.ts:54` returns the
> 403 and `:57` returns the 401, so neither path falls through to the handler.
> The same `return` is on `requireAuth` at `:44`. The role test also changed
> shape: it now accepts `admin`, `manager` or `developer` rather than a single
> `user` role, matching the roles the schema actually issues.

### P0-4: Refresh token uses same JWT secret as access token

**File:** `apps/api/src/server.ts` line 16, `apps/api/src/routes/auth/device.ts` lines 57-60
**Severity:** High | **Exploitability:** Moderate

Both access and refresh tokens are signed with `JWT_SECRET`. The `.env.example` defines `JWT_REFRESH_SECRET` but it is never used. This means:
- A stolen access token can be used as a refresh token (and vice versa)
- There is no way to revoke access tokens independently of refresh tokens

The refresh endpoint at `/v1/auth/refresh` verifies the token with the same secret:

```typescript
// Line 81 -- uses same jwt instance (same secret) for refresh
const payload = await request.jwtVerify()
```

**Fix:** Register a second `@fastify/jwt` instance with a different name for refresh tokens:

```typescript
await server.register(jwt, { secret: process.env.JWT_SECRET!, namespace: 'access' })
await server.register(jwt, { secret: process.env.JWT_REFRESH_SECRET!, namespace: 'refresh' })
```

> **STATUS 2026-11-05: RESOLVED.** Implemented as written, now in
> `apps/api/src/app.ts:41-42` (the registration moved out of `server.ts` with
> `buildServer()`, BW-03). The two namespaces are used end to end:
> `device.ts:128-129` signs the access token with `fastify.jwt.access` and the
> refresh token with `fastify.jwt.refresh`, and `/v1/auth/refresh` at `:151`
> verifies through `request.refreshJwtVerify`. `JWT_REFRESH_SECRET` is no longer
> declared-but-unused. The route tests cover both directions of the swap: a
> refresh token is rejected on dashboard routes and an access token is rejected
> at `/v1/auth/refresh`.

### P0-5: Token "hash" is not a hash -- stores raw token suffix

**File:** `apps/api/src/routes/auth/device.ts` lines 63-66
**Severity:** High | **Exploitability:** Moderate

The `deviceTokens` table stores `tokenHash: accessToken.slice(-16)` which is NOT a hash. It is a raw suffix of the JWT. This:
1. Provides no cryptographic protection if the DB is compromised
2. Is never validated against on any subsequent request (dead code)
3. The last 16 chars of a JWT are part of the signature, making them predictable with the secret

**Fix:** Use a proper hash (e.g., `crypto.createHash('sha256').update(accessToken).digest('hex')`) or remove the dead code entirely.

> **STATUS 2026-11-05: RESOLVED.** `apps/api/src/routes/auth/device.ts:132` is
> `createHash('sha256').update(accessToken).digest('hex')`, the exact fix
> proposed. A test asserts the stored value is 64 characters and is not the token
> itself. Point 2 of the finding stands unchanged: the hash is written at
> verification and still nothing reads it back, so token revocation is stored but
> not enforced. That is dormant rather than dangerous now that the value is a
> real hash. No ticket owns wiring it up.

## P1 -- High (Fix before production use)

### P1-1: Device registration skips the pending/verification flow

**File:** `apps/api/src/routes/auth/device.ts` lines 22-76
**Severity:** High

The schema defines `pendingDevices` with a verification code flow (6-char alphanumeric code), and the shared types define `RegisterDeviceResponse` with `pendingId`, `code`, and `expiresAt`. However, the actual implementation skips all of this and immediately creates the device + returns JWT tokens.

This means anyone who knows a user's email can register a device and get full API access to that user's data. There is no verification step.

**Impact:** An attacker who knows an employee's email can impersonate them.

**Fix:** Implement the pending device flow: create a `pendingDevices` row with a code, return the code, and require a separate `/verify-device` endpoint call (initiated from the dashboard) before issuing tokens.

> **STATUS 2026-11-05: RESOLVED.** Built as described.
> `apps/api/src/routes/auth/device.ts:31-70` is now step one: it inserts a
> `pendingDevices` row with a generated code and a 15-minute expiry, and returns
> `pendingId`, `code` and `expiresAt`. It issues no tokens. Step two at `:73-146`
> matches on `pendingId` plus `code`, requires `verifiedAt` to be null and
> `expiresAt` to be in the future, and only then creates the device and signs
> tokens. A used code cannot be replayed because `verifiedAt` is stamped at
> `:121-124`. A test covers registration returning a code and no tokens.

### P1-2: No org-scoping on dashboard queries -- IDOR vulnerability

**File:** `apps/api/src/routes/dashboard/overview.ts` line 10, and all dashboard routes
**Severity:** High | **Exploitability:** Trivial (once auth is added)

The `orgId` comes from the query string with no validation against the authenticated user's org. Even when auth is added (P0-2), users could query data from other organizations by passing a different `orgId`.

```typescript
// Line 10 -- orgId from query, not from JWT
const { orgId, date } = request.query
```

**Fix:** Always use `request.user.orgId` from the JWT payload instead of `request.query.orgId`.

> **STATUS 2026-11-05: RESOLVED.** All five routes read the org from the token
> and never from the query: `overview.ts:18`, `leaderboard.ts:20`,
> `trends.ts:18`, `activity.ts:18` and `projects.ts:18` each open with
> `const orgId = request.user.orgId`. `orgId` was dropped from every query
> schema, so passing one has no effect rather than being validated against the
> token. This is the IDOR fix and it has a regression test: a token for org A
> reading org B's data with `orgId` in the query. Reverting `/overview` to read
> the query param turns that test red and nothing else.

### P1-3: Unbounded JSONL file reads in codeburn collector

**File:** `apps/agent/src/collectors/codeburn.ts` lines 28-94
**Severity:** High (availability)

The codeburn collector recursively scans ALL `.jsonl` files under `~/.claude/projects/` and reads each one entirely into memory with `readFileSync`. Based on the user's real data (36,870 calls all-time), these files could be hundreds of MB.

```typescript
// Line 41 -- reads entire file into memory
const lines = readFileSync(file, 'utf8').split('\n').filter(Boolean)
```

**Impact:** OOM crash or multi-second blocking on large histories.

**Fix:** Use streaming line-by-line reads. For Bun, use `Bun.file(path).text()` with a line iterator, or Node's `readline.createInterface` with a file stream. Also add a file size check and skip files larger than a threshold.

> **STATUS 2026-11-05: RESOLVED.** Both halves of the fix are in
> `apps/agent/src/collectors/codeburn.ts`. The size guard is at `:52-53`:
> `statSync(file)` against a `MAX_FILE_SIZE` of 50 MB declared at `:9`, skipping
> anything larger. Reading is line by line at `:58` through
> `createInterface({ input: createReadStream(file, ...), crlfDelay: Infinity })`.
> No `readFileSync` remains in the file. A test proves the guard short-circuits
> rather than reading and discarding: it fakes the reported size and asserts
> `createReadStream` is never called.

### P1-4: `spawnSync` blocks the event loop during ccusage collection

**File:** `apps/agent/src/collectors/ccusage.ts` lines 32-36
**Severity:** Medium (agent-only, but blocks for up to 60s)

`spawnSync` with a 60-second timeout blocks the entire process. When backfilling 7 days (`--last-7`), this runs 7 times sequentially -- up to 7 minutes of blocking.

**Fix:** Use `Bun.spawn` or `child_process.spawn` (async) and collect output via streams.

> **STATUS 2026-11-05: RESOLVED.** `apps/agent/src/collectors/ccusage.ts:20`
> uses async `spawn(cmd, args, { stdio: ['ignore', 'pipe', 'pipe'] })` and
> collects output from the streams. No `spawnSync` remains in the file. The
> backfill path was also reworked into a single pass (commit `182699a`) rather
> than one invocation per day, so the seven sequential runs the finding describes
> no longer happen either.

### P1-5: Fire-and-forget snapshot rebuild with no retry

**File:** `apps/api/src/routes/usage/submit.ts` lines 52-54
**Severity:** Medium

The snapshot rebuild is fire-and-forget with only a log on error. If it fails, the dashboard will show stale/zero data for that user+date with no mechanism to retry.

```typescript
rebuildDailySnapshot(fastify.db, jwt.userId, payload.date).catch((err) => {
  fastify.log.error({ err, userId: jwt.userId, date: payload.date }, 'Snapshot rebuild failed')
})
```

**Fix:** At minimum, add a retry queue (Redis-based). Alternatively, make the snapshot rebuild synchronous within the request (it's only 3 queries) so failures are visible to the caller.

> **STATUS 2026-11-05: RESOLVED** via the second option, not the first. There is
> no retry queue. `apps/api/src/routes/usage/submit.ts:40-64` wraps the writes in
> `fastify.db.transaction()` and awaits `rebuildDailySnapshot` at `:61` inside
> it. The `.catch()` that swallowed the error is gone, so a failed rebuild now
> rolls the events back and surfaces as a 500. The agent's retry re-submits them.
> That is stronger than the retry queue proposed here: there is no window where
> spend is recorded but missing from the snapshot. Delivered by BW-15.

### P1-6: No input validation on dashboard query parameters

**File:** `apps/api/src/routes/dashboard/overview.ts` line 10, all dashboard routes
**Severity:** Medium

The `orgId` and `date` parameters are used directly in queries without format validation. While Drizzle ORM parameterizes queries (preventing SQL injection), invalid formats could cause unexpected behavior:
- `date` is not validated as YYYY-MM-DD
- `orgId` is not validated as UUID
- `days` in trends route is parsed with `Number()` which returns `NaN` for garbage input (handled by `|| 30` fallback)

**Fix:** Add Zod schemas for query parameters:

```typescript
const QuerySchema = z.object({
  orgId: z.string().uuid(),
  date: z.string().regex(/^\d{4}-\d{2}-\d{2}$/),
})
```

> **STATUS 2026-11-05: RESOLVED.** Every dashboard route now declares a Zod
> `QuerySchema` and runs `safeParse`, returning 400 with `error.flatten()` on
> failure: `overview.ts:8-12` and `:19-22`, `leaderboard.ts:8-14`,
> `trends.ts:8-12`, `activity.ts:8-12`, `projects.ts:8-12`. Dates are checked
> against `/^\d{4}-\d{2}-\d{2}$/`. The `days` parameter in trends is
> `z.coerce.number().int().min(1).max(90)`, so garbage is a 400 rather than a
> `NaN` falling through to a default. The `orgId` half of the finding is moot:
> it is no longer a query parameter (see P1-2). The schemas are duplicated
> per route rather than shared, which the Suggested Abstractions section flags.

## P2 -- Medium (Fix before scaling)

### P2-1: `numeric` columns return strings from Drizzle, inconsistent handling

**File:** `apps/api/src/routes/dashboard/leaderboard.ts` lines 50-58, `apps/api/src/services/snapshot.service.ts`
**Severity:** Medium

Drizzle returns `numeric` columns as strings (PostgreSQL behavior). Some places use `.mapWith(Number)` (overview.ts), some use manual `Number()` casts (leaderboard.ts), and some pass strings directly. The `costUsd` field in `usageEvents` is `numeric` but is set as `String(e.costUsd)` -- this works but is fragile.

**Impact:** Potential type mismatches, NaN in calculations if a value is unexpectedly null.

**Fix:** Standardize: always use `.mapWith(Number)` on numeric select fields, or create a helper.

> **STATUS 2026-11-05: RESOLVED**, and the finding was right that it was more
> than cosmetic. `leaderboard.ts:38-50` now applies `.mapWith(Number)` to every
> numeric field instead of manual casts, and `overview.ts:78-90` and
> `trends.ts:44-52` do the same. `snapshot.service.ts:14-17` adds the helper the
> fix asked for, `toNumber`, used at `:40`.
>
> That helper closed a real bug, found when BW-13 added tests. The code read
> `row.cost ?? 0` and trusted `.mapWith(Number)` to have converted the postgres
> `numeric`. A string reaching it would make `+` concatenate rather than add:
> `'1.5' + '2.25'` is `'1.52.25'`, so the day's total would be silently wrong
> with nothing thrown. `toNumber` coerces and falls back to 0 on anything
> non-finite. Reverting it turns two tests red. The `String(...)` casts on the
> write path at `:90-100` remain and are correct for inserting into a `numeric`
> column.

### P2-2: Cache key does not differentiate by auth context

**File:** `apps/api/src/routes/dashboard/overview.ts` line 16, all dashboard routes
**Severity:** Medium

Cache keys are `bw:overview:${orgId}:${date}` -- they don't include any user context. If role-based data filtering is added later, cached data from one role could be served to another.

Additionally, the trends cache key is `bw:trends:${orgId}:${days}` which doesn't account for the current date -- fetching "last 30 days" today and tomorrow would return the same cached result.

**Fix:** Include the current date in time-relative cache keys:

```typescript
const cacheKey = `bw:trends:${orgId}:${days}:${new Date().toISOString().slice(0, 10)}`
```

> **STATUS 2026-11-05: RESOLVED.** The stale-window bug is gone, by a different
> route than the fix proposed. `trends.ts:24-37` resolves `days` into concrete
> `fromDate` and `toDate` values before building the key, so the key is
> `bw:trends:${orgId}:${fromDate}:${toDate}` and a "last 30 days" request made
> today and tomorrow produces two different keys. The other four routes key on
> resolved dates the same way.
>
> On the auth-context half: `orgId` in every key now comes from the JWT rather
> than a query param (P1-2), so one org cannot read another's cached entry. No
> role-based filtering exists yet, so there is nothing further to key on. If it
> is ever added, the role has to go into the key.

## Architecture Assessment

### What works well
1. **Shared package with Zod schemas** -- excellent pattern for API contract validation
2. **Drizzle schema design** -- proper use of unique constraints, indexes, and JSONB types
3. **Pre-aggregated snapshots** -- smart denormalization for dashboard query performance
4. **Agent collector interface** -- clean separation of ccusage vs codeburn collectors
5. **Upsert semantics** -- `onConflictDoNothing`/`onConflictDoUpdate` prevents duplicate data

### Architecture gaps
1. **No transaction boundaries** -- `upsertUsageEvents` + `upsertEnrichment` + snapshot rebuild are 3 separate DB operations with no transaction wrapper. A failure between them leaves inconsistent state.
2. **No error boundary between dashboard sub-routes** -- a crash in one route handler could affect the shared Fastify instance.
3. **Dashboard fetches data at render time with no ISR/caching strategy** -- every page load hits the API.
4. **No health check for dependencies** -- `/health` returns `{ ok: true }` without checking DB or Redis connectivity.

> **STATUS 2026-11-05**, gap by gap.
>
> 1. **No transaction boundaries. RESOLVED (BW-15).**
>    `apps/api/src/routes/usage/submit.ts:40-64` wraps the writes in
>    `fastify.db.transaction()`. Four operations, not the three listed here: the
>    `devices.lastSeenAt` touch at `:53-56` was in the same unprotected sequence.
>    The WebSocket Neon driver was kept specifically to allow this, since
>    `neon-http` cannot hold a transaction across statements.
> 2. **No error boundary between dashboard sub-routes. RESOLVED**, though the
>    premise overstated the risk. Fastify's plugin encapsulation already kept a
>    throwing handler from affecting sibling routes. What was genuinely missing
>    was a top-level handler, and `app.ts:22-28` now provides one.
> 3. **Dashboard fetches at render time with no caching strategy. STILL OPEN.**
>    `apps/dashboard/src/lib/api.ts:23` still passes `cache: 'no-store'`, so
>    every page load reaches the API. The impact is smaller than it looks: the
>    API caches each dashboard response in Redis for 300 seconds, so the load
>    lands on Redis rather than postgres. **No ticket owns this.**
> 4. **No health check for dependencies. RESOLVED (BW-16).** `app.ts:52-70`
>    runs `select 1` and a Redis `PING` under `Promise.allSettled`, so one dead
>    dependency still reports on the other, and returns 503
>    `{ ok: false, failed: [...] }` naming what failed. Driver errors go to the
>    log, not the response, because both drivers put the host in the message and
>    the Redis URL carries a password. A test asserts no credentials reach the
>    body.
